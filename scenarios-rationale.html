Scenario 1 — Retain Team Competency — No Client Risk

S1
Retain Team Competency — No Client Risk
FY27 total: £71.5M
Design intent Partners exit only once their Kraken replacement has 3 months of on-the-job experience. This sets a principled constraint on exit pace: you can only exit as fast as you can hire and onboard qualified replacements. At 8 hires/mo starting Jul 26, the first cohort is ready Oct 26 — exits begin then and run at 8/mo. Team stays at 500 throughout. All partners gone Sep 27.
Key trade-off Zero delivery risk — no client is ever under-resourced — but exits are slow and FY27 cost is the highest of all three scenarios. The 3-month pipeline constraint means Jul–Sep 26 is fully paid at the current run rate (£6,090k/mo) with no cost relief. The saving only starts Oct 26. By Jan 27 (FY27 close), 63 of 95 partners are still on board — the bulk of the cost saving falls into FY28.

Scenario 2 — Balanced

S2
Balanced
FY27 total: £67.0M
Design intent Front-load exits to drive savings before Jan 27, while retaining a specialist core of 19 permanently. Represents a pragmatic middle ground — strong cost improvement without the full operational risk of a complete exit.
Key trade-off 76 partners exit in 7 months (~11/mo), each replaced 1:1. The 19 retained are treated as long-term specialists the business genuinely needs. They remain in the cost base permanently. If that retention number changes, the FY27 total shifts accordingly (each retained partner costs +£19.839k/mo vs an exited one).

Scenario 3 — Hit Budget / Run Under-Strength

S3
Hit Budget / Run Under-Strength
FY27 total: £59.8M ✓
Action & Consequences Action: All partners roll off by Sep 26. Kraken hires stagger in at 12/mo from Jul.
Consequences: Backfilling not possible in time · All clients will be under-resourced Sep 26–Jan 27 · Replacement hires are inexperienced.
Design intent Exit all 95 partners in a compressed 3-month window (~32/mo, Jul–Sep), while hiring replacements at 12/mo. This deliberately decouples exits from hires — the only mechanism that lets S3 land at £59.8M within the £59M budget envelope. Full team of 500 is restored Feb 27, one month into FY28.
Key trade-off — why the team goes under-strength If hires joined 1:1 same-month as exits (as in S1/S2), the FY27 total would be ~£63M even with fast exits. Slowing hires to 12/mo means internal costs rise by only £101k/mo (vs £279k/mo at 33/mo). The saving: ~£3.2M vs same-pace hiring. The cost: team size dips from 500 to 441 in Sep 26 (−59 capacity gap, −11.8%), recovering to 500 by Feb 27. Every amber/red month in the table below represents a real delivery risk — all client commitments must be reviewed against this reduced headcount.
Why £59.8M and not exactly £59.0M? The £59M figure is the total org budget; the headcount model sits inside it. The minimum FY27 headcount total under any phased exit is ~£59.8M, driven by the sunk £30.5M plus 7 months of operational spend. Compressing further would require either negative hires or a different FY27 definition. £59.8M is the floor with this model.

Competency Impact Model

Framework & assumptions
Competency loss is measured against 400 effective resource (500 total team × 89%, minus leadership roles — TDs, GPLs, ODLs, HDLs — leaving ~400 delivery resource directly working on meterpoints).

Partners on board = 1.0 FTE competency each (full tenure).
New hires ramp linearly from 0 → 1.0 FTE over 6 months. Month 1 = 1/6 competent, Month 6 = fully competent.
Empty seats (S3 only) = 0 competency — the position simply does not exist yet.
Base Kraken team (405) is excluded — fully competent throughout and not affected by the transition.

All three scenarios are planned reductions. The 3-month planning window is built into each exit schedule (recruitment starts in advance), so the 6-month competency clock starts when the hire joins — not earlier.

% of effective resource competency lost — by month

Gap = (95 − partner_competency − hire_competency) ÷ 400. Hire competency = tenure_months ÷ 6, capped at 1.0.

How to Update the Scenarios

1
If a rate changes (PARTNER_RATE, REPL_RATE, or FIXED_K) Update the constants at the top of partner-scenarios.html (search for const FIXED_K). Recalculate all monthly totals using the formula above, then update the hardcoded table rows for whichever scenario is affected. Update this document to match.
2
If the S1 exit pace or pipeline delay changes Edit HC.s1 in the JS. S1 constraint: no exits until month X+3 where X is the month hiring starts (currently Jul 26, so exits start Oct 26). If the hiring rate changes (currently 8/mo), update the HC array accordingly and recalculate table rows using the standard formula: internal = FIXED_K + (95−p) × REPL_RATE, partner = p × PARTNER_RATE. Update the FY27 cumulative column and Jan 27 total. Note: Jul–Sep rows stay flat at £6,090k/mo as long as no exits occur. Update the metric cards. Update this document.

If the S2 exit pace changes Edit HC.s2 in the JS. The chart will update automatically. Recalculate the table rows using the standard formula. Update the FY27 cumulative column and Jan 27 total. Update metric cards. Update this document.
3
If the S3 exit pace or hire rate changes Edit HC.s3 (controls partner headcount for the chart). Also update the table manually — S3 internal costs use the delayed-hire formula (FIXED_K + hires_cumulative × REPL_RATE), not the standard (95−p) formula. The chart will show a slightly different Kraken bar than the table reflects; this is expected and noted in the mechanic text. Update both metric cards and the rationale text. Update this document.
4
If the start headcount (95) or FY definition changes Update START, FY_SUNK_K, and the sunk row value (currently £30.5M = 5 mo × £6,090k total). All cumulative FY27 projected figures need to be recalculated from scratch for all three scenarios. Update the budget context table above if total org budget also changes.
5
Quick sanity check after any change Jan 27 FY27 projected = sunk + sum(Jul–Jan monthly totals). If using delayed hires (S3), verify internal costs track the hire schedule, not the exit schedule. Net saving per exit must equal PARTNER_RATE − REPL_RATE; if either rate changes, update the formula note in the mechanic text.
